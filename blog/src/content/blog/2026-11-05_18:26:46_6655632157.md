## 复现条件与诊断顺序

假设 API 模块发布 `2.0.0-SNAPSHOT`，DTO 新增了 `metricCount` 和 `deviceKind` 字段，消费服务开始调用 `getMetricCount()`、`getDeviceKind()`。如果消费服务或 CI 缓存仍保存旧的 `device-api` JAR，编译器就会提示找不到这些方法。

先从源码确认字段，再查看消费模块声明的依赖版本：

```bash
rg -n 'metricCount|deviceKind' device-api/src/main/java
mvn -pl device-consumer dependency:tree \
  -Dincludes=com.example.platform:device-api
```

把 `device-consumer`、`device-api` 和包名替换成实际模块名。`dependency:tree` 用来确认依赖坐标和版本；它显示 `2.0.0-SNAPSHOT` 时，仍需检查 Maven 实际选择的快照二进制。

如果本地或 CI 已缓存旧版 JAR，以下命令可能复现错误：

```bash
mvn -pl device-consumer clean compile
```

这依赖于缓存中确实存在旧 SNAPSHOT。全新环境可能直接下载最新快照，因此未必能复现。Maven 默认按仓库更新策略检查 SNAPSHOT；CI 若跨任务缓存整个本地仓库，问题更容易持续。

## 检查实际解析的 JAR

找到本地仓库里的 API JAR，并用 `javap` 查看它实际包含的方法：

```bash
API_JAR="$HOME/.m2/repository/com/example/platform/device-api/2.0.0-SNAPSHOT/device-api-2.0.0-SNAPSHOT.jar"
javap -classpath "$API_JAR" com.example.api.DeviceSummary
```

如果输出没有 `getMetricCount()` 或 `getDeviceKind()`，说明当前二进制不含消费代码需要的方法。若源码有字段而 JAR 没有，问题在依赖产物或解析版本，不在消费方的 getter 调用。对 Lombok DTO，可用同一方式核对已编译 JAR，避免只凭源码推断生成结果。

在 API 多模块项目根目录发布更新的快照。`deploy` 会执行此前的默认生命周期阶段，包括编译和测试，然后上传产物：

```bash
# 部署到 POM 配置的远程仓库
mvn -pl device-api -am clean deploy
```

若只需在本机的另一个项目验证，可用 `install` 将产物放入本地 Maven 仓库，而不上传到远程仓库：

```bash
mvn -pl device-api -am clean install
```

## 修复 CI 并验证

让消费服务强制检查远程 SNAPSHOT 更新，再从干净的 `target` 目录编译：

```bash
mvn -U -pl device-consumer clean compile
```

GitLab 构建脚本也应带上 `-U`，例如：

```yaml
script:
  - mvn -U clean package -DskipTests
```

`-U` 会强制检查远程仓库里的更新快照。修复后执行消费模块测试：

```bash
mvn -U -pl device-consumer clean test
```

如果需要执行项目绑定在 `verify` 阶段的集成检查，可运行：

```bash
mvn -U -pl device-consumer clean verify
```

本次排查中，源码包含所需 DTO 字段；从内部 Maven 仓库重新解析到的当前快照 JAR 也包含对应 getter。本地执行干净编译成功。消费项目的 GitLab 配置缓存了 Maven 本地仓库，原构建命令没有 `-U`，所以旧快照是最符合证据的原因；失败任务实际使用的 JAR 未留档，因此应以更新 CI 后的 GitLab 重跑结果作最终确认。CI 命令已调整为 `mvn -U package`。本地只运行了编译，没有运行测试。

## clean、SNAPSHOT 和测试的区别

`clean` 删除上次构建生成的项目文件，通常是各模块的 `target`。它不会删除或更新 `$HOME/.m2/repository` 中缓存的依赖。因此：

- 旧的本地编译产物可用 `mvn clean ...` 排除。
- 旧的远程 SNAPSHOT 依赖要用 `mvn -U ...` 触发更新检查。
- `mvn clean deploy` 会先执行 clean，再执行默认生命周期直到 deploy；deploy 会上传产物到 POM 配置的远程仓库。Maven 生命周期顺序见[官方生命周期指南](https://maven.apache.org/guides/introduction/introduction-to-the-lifecycle.html)。
- `-DskipTests` 跳过测试执行，但 Maven 仍可能编译测试源码；要运行测试用 `mvn test` 或更后面的生命周期阶段。

`-U` 的定义见 [Maven CLI 选项](https://maven.apache.org/ref/3.9.8/maven-embedder/cli.html)：它强制检查远程仓库中的更新 SNAPSHOT。排查时可先执行 `dependency:tree`，再用 `javap` 检查最终 JAR；不要只因为加了 `clean` 就认为依赖缓存已刷新。

## 另一个编译错误要单独诊断

同一轮排查还出现过 Lombok `onConstructor_` 属性无法解析的测试错误。本地用项目解析到的 Lombok 依赖执行 `clean test-compile` 成功，但没有在 GitLab 使用的完整构建环境中重现。因此不能把它归因于这次 SNAPSHOT 缓存问题，也不能说 `clean` 已修复它。遇到这类错误时，应在失败任务中记录实际 JDK、Lombok 解析版本、编译器插件和注解处理配置，再用相同环境重跑编译。

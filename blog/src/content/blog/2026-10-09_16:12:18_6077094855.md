# 把源码分析变成可回顾的文章：一个跨会话发布 Skill 的设计

在使用 agent 分析项目时，源码调用链、bug 根因和架构取舍经常只留在聊天记录中。过一段时间再看，需要重新找到会话、理解当时的上下文，甚至重复分析。我们希望把这些结果整理成文章，在线查看，也能在后续会话中继续修订。

这次给 all-in-github 项目增加跨会话发布能力，目标只有三个：简单、安全、使用方便。最终得到的是一个纯说明型 skill：约定发布流程和完成标准，由 agent 使用当前环境中可用的 GitHub 工具执行。

## 先复用已经存在的发布链路

all-in-github 已经把 GitHub Issues 用作内容管理入口。其中，带有 `Note` 标签的 issue 是文章容器，每条评论对应一篇文章。

发布链路可以表示为：

```text
当前会话的分析
    → 可独立阅读的 Markdown
    → Note issue 中的一条评论
    → GitHub Actions 生成博客内容
    → GitHub Pages 部署文章
```

这意味着 skill 只需要负责前半段：从分析中提炼文章，然后写入评论。生成 Markdown、提交内容和部署站点继续由仓库原有自动化完成，无需再增加一个发布服务。

文章使用评论 ID 作为 slug。后续修订编辑同一条评论，便能保持文章地址，也方便跨会话继续操作。

## 从预制脚本简化到流程说明

最初的方案是在 skill 中附带 Python 发布脚本和 shell 编辑器入口，把检查与上传做成固定命令。这样的方案可以用程序强制校验账号、评论归属和重复内容，但也带来了额外代码、运行依赖以及需要维护的调用方式。

进一步明确需求后，我们发现真正需要复用的是“如何发布”，而不是某一套上传实现。不同会话可能具有不同工具：有的可以使用 GitHub 连接器，有的可以执行 GitHub CLI，有的能够调用已经授权的 API。

因此，最终去掉预制脚本和独立配置文件，将必要信息收敛到 `SKILL.md`：

1. 整理文章。
2. 组成评论。
3. 检查发布条件。
4. 创建或更新评论。
5. 保存回执并返回发布结果。

skill 说明每一步要得到什么结果，把具体工具与调用方式交给 agent。这个选择减少了技能包的复杂度，同时也意味着安全校验由 agent 遵循流程执行，不再由程序强制拦截。

## 文章需要能脱离聊天上下文阅读

发布文章不能只是复制整段聊天记录。文章需要让没有参与分析的人也能理解问题、证据和结论。

不同分析内容可以按需要组织：

| 内容 | 应保留的重点 |
| --- | --- |
| 源码分析 | 分析问题、关键调用链或数据流、源码证据、结论 |
| bug 分析 | 现象与触发条件、根因、解决方案、实际验证与未验证项 |
| 架构设计 | 约束、方案、取舍、模块边界及实施建议 |

标题、一句话摘要和少量主题标签由 agent 根据内容拟定，不必逐项向用户索取。事实、推断和建议应分别表达，验证结果只能写实际执行过的内容。

正文保存在被分析项目的 `docs/` 中。源码引用使用确定 commit 的链接，或者相对路径与符号名；代码片段只保留解释结论所需的部分。公开前检查凭据、内部地址和个人数据，未经公开授权的私有源码改用脱敏原理或伪代码。

## 评论格式是必须明确的约定

现有生成器通过评论开头的 HTML 注释提取标题、标签和摘要。格式示意如下；这里将注释定界符转义，避免生成器把示例本身移除：

```text
&lt;!-- title: 文章标题 --&gt;
&lt;!-- tags: 源码分析,主题 --&gt;
&lt;!-- description: 一句话摘要 --&gt;

## 正文

文章内容。
```

实际发布的元数据使用正常 HTML 注释。元数据值保持非空、单行且不含注释定界符，标签使用英文逗号分隔。正文不带 frontmatter，也不重复这些元数据。

另一个容易忽略的细节是：生成器会移除正文中所有 HTML 注释，包括代码示例中的注释。需要展示这些内容时应转义定界符。

分类与标签也有不同来源：issue 的 labels 决定文章分类，评论中的 tags 描述具体主题。发布一篇文章不需要顺便修改容器标签。

## 安全边界放在真正发生写入的位置

用户要求分析、整理草稿或设计 skill，不等于要求公开文章。只有明确要求发布或更新时，agent 才执行写入；这个请求已经是当前文章的授权，不再重复询问是否发布。

写入前需要检查实际发布身份和目标：

- 发布账号必须等于目标仓库 owner，现有工作流只处理 owner 的评论。
- 目标必须是开放的 issue，带有 `Note`，且不含会跳过生成的 `Blog`、`Published` 或 `Publishing`。
- 更新时核实评论所属 issue 和作者，使用明确的 comment ID。
- 凭据交给现有工具管理，不写入正文或 skill。

新建评论前读取已有评论及必要分页，发现当前账号已经发布相同完整内容时复用。请求超时、结果不明时先查询评论，再决定是否重试。同一篇文章串行提交，避免多个会话同时创建重复评论。

这些约定只覆盖当前发布任务。创建新的文章容器、修改 issue 标签等操作，需要有相应的用户请求。

## 默认位置既要方便，也要能调整

本次将默认文章容器设为 [issue #24「日志」](https://github.com/byodian/all-in-github/issues/24)，适合持续记录源码分析、问题排查和设计思考。

用户可以直接说：

```text
$publish-note-blog 把刚才的源码分析发布成文章。
```

也可以修改默认发布位置：

```text
$publish-note-blog 将 issue 23 设为默认发布位置。
```

agent 先检查目标 issue 是否满足发布条件，再修改用户级安装版本 `SKILL.md` 中的“默认目标”。后续会话读取这个默认值，不需要增加独立配置文件。

这里区分两种意图：

- “这篇文章发布到 issue 23”：只影响这一次。
- “将 issue 23 设为默认”：保存为后续发布的默认值。

默认位置变化不会迁移旧文章。更新已发布文章时，继续使用原评论所在的 issue。更换仓库时，issue 编号和博客地址需要重新确定，不能沿用旧仓库的目标。

## 跨会话靠技能发现和发布回执接续

版本源保存在项目的 `.codex/skills/publish-note-blog/`，安装时复制到用户级 skill 目录。Codex 的用户级目录是 `~/.agents/skills`，可用于跨项目发现技能，具体规则见 [OpenAI 官方文档](https://learn.chatgpt.com/docs/build-skills)。

最终技能包只有 `SKILL.md` 和可选的界面元数据 `agents/openai.yaml`。发布不要求从博客仓库启动，也不依赖本地 Python 或 Node；实际 GitHub 工具和认证由当前会话提供。

跨会话可用不意味着新会话能自动读取旧聊天。因此，每次发布还需要把仓库、issue、comment ID、评论地址和文章地址保存在当前项目的 `docs/<主题>.publish.json` 中。后续会话拿到正文和回执，就能明确地更新原文章。

用户修改过默认目标后，重新安装时也需要保留这项设置，避免覆盖成分发版本的默认值。

## 发布成功要有明确的完成标准

保存评论和文章上线是两个阶段。GitHub 返回评论地址，只能说明内容写入成功，后续仍需自动生成和部署。

agent 应返回评论链接和文章链接，并说明当前状态。只有确认本次部署成功，或者核实线上文章内容后，才能报告已经上线。不能把任务列表中的最新任务直接当作这篇文章的部署结果，也不能因为部署尚未结束而再创建一条评论。

本文用于这套纯流程 skill 的首次真实发布验证：检查目标和身份，按约定组成评论，保存回执，再关联生成与部署结果。这样既测试了上传，也测试了文章是否真的能在线阅读。

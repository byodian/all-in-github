## 先理解提交 ID 为什么会变化

Git 提交对象记录了文件树、父提交、作者和提交者信息以及提交消息。Git 根据对象内容计算 ID，所以改消息会生成新的提交对象和新的 ID。引用了旧提交作为父节点的后代，也要改为引用新 ID，因此这些后代的 ID 会跟着变化。受影响范围沿提交图的父子关系传播，不是按提交时间决定。[Git 数据模型](https://git-scm.com/docs/gitdatamodel)描述了提交对象及其父提交关系。

例如，改写一条分支上的提交时，如果后面有一个把这条分支合并进来的 merge commit，merge commit 也会重写；另一条并非目标提交后代的分支通常保持原样。

## 方法对比

## 只改最新一条：`git commit --amend`

```sh
git commit --amend -m "docs: clarify migration safety"
```

`--amend` 用一个新提交替换当前 `HEAD`。如果只想改消息，先检查暂存区，确保没有意外暂存的文件；`--amend` 也可以把暂存区内容一起纳入新提交。完整行为见 [`git-commit`](https://git-scm.com/docs/git-commit)。

这适合还在本地整理的最新提交。提交已经推送且其他人基于它继续工作时，改写会改变共享历史，需要先协调，再更新远端分支。

## 修改更早的提交：交互式 `rebase`

```sh
git rebase -i <目标提交的父提交>
```

在打开的列表里，将目标提交对应的 `pick` 改成 `reword`，保存后按提示编辑消息。Git 会重放这条提交及后续提交；即使改动内容相同，被重放的提交也会得到新的 ID。交互式命令和 `reword` 的含义见 [`git-rebase`](https://git-scm.com/docs/git-rebase)。

分支里有 merge commit 且要保留分支结构时，可以使用：

```sh
git rebase -i --rebase-merges <目标提交的父提交>
```

`--rebase-merges` 会重建合并结构。重放时，过去在合并冲突中做的手动选择可能需要重新处理。它适合需要保留合并拓扑的历史整理；普通线性提交序列用 `git rebase -i` 即可。

## 移植一条改动：`cherry-pick`

```sh
git cherry-pick --edit <提交 ID>
```

`cherry-pick` 把指定提交引入的改动应用到当前分支，并在当前分支创建一个新提交。`--edit` 允许编辑这个新提交的消息；原提交不会被修改。[`git-cherry-pick`](https://git-scm.com/docs/git-cherry-pick) 将它定义为把已有提交记录的改动重新应用到当前分支。

因此，`cherry-pick` 更适合把一个修复从开发分支移到发布分支。若目标已经在当前分支历史里，直接 cherry-pick 可能重复应用改动。想替换原提交并保留原来的提交图，还需要重放其后代或重建合并关系；这时交互式 rebase 通常更直接。

## 保留提交 ID：`git notes`

```sh
git notes add -m "Retested against the staging database" <提交 ID>
```

Git notes 把附加说明放在独立的 notes 引用中，不改变原提交对象或提交消息。它适合补充测试结果、审查记录和背景信息。Notes 引用需要单独同步；如果团队其他成员也要看到 notes，需要一并推送对应引用。详见 [`git-notes`](https://git-scm.com/docs/git-notes)。

如果你需要改变代码托管平台提交列表中显示的标题，notes 做不到这一点；它保留原提交消息，只增加一条关联说明。

## 批量改写历史：`git-filter-repo`

要批量清理历史中的文件、敏感数据或提交元数据，可以使用 [`git-filter-repo`](https://github.com/newren/git-filter-repo)。它适用于有明确筛选规则的仓库级改写，改写后需要重新检查引用、标签和协作者的克隆。

Git 的 [`git-filter-branch` 手册](https://git-scm.com/docs/git-filter-branch)专门警告该命令有许多容易造成错误历史的陷阱，并建议改用 `git-filter-repo`。为改一条提交消息而运行批量历史过滤器，通常不如 `rebase -i` 清楚。

## 已推送的历史如何更新

历史改写会让本地和远端分支出现不同的提交 ID。若团队已经基于旧提交继续开发，先沟通改写范围和恢复方式。确认远端没有新提交后，使用 `--force-with-lease` 更新分支：

```sh
git fetch origin
git push --force-with-lease origin <分支名>
```

`--force-with-lease` 会在远端分支不再符合本地预期时拒绝更新，降低覆盖他人新提交的风险；它不能代替团队协调。参数行为见 [`git-push`](https://git-scm.com/docs/git-push)。

## 按目标选择

- **刚创建的最新提交，尚未共享**：用 `git commit --amend`。
- **较早提交需要改消息**：用 `git rebase -i` 的 `reword`；需要保留 merge 结构时加 `--rebase-merges`。
- **把一项改动带到另一条分支**：用 `git cherry-pick`。
- **提交 ID 和原消息都要保留，只补充背景**：用 `git notes` 或新增一条说明提交。
- **按规则批量改写整个仓库**：考虑 `git-filter-repo`，先制定可恢复的迁移方案。

核心判断是你要改哪一层：改当前消息、重写既有历史、移植一项补丁、附加说明，还是批量清理仓库。选对目标后，再根据提交是否已推送、是否有协作者和是否包含 merge commit，决定是否重写及如何同步。

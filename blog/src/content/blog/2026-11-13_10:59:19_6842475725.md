一个静态站点的发布流程，应能回答四个问题：线上文件来自哪个提交、哪些检查已通过、谁有权发布，以及出错后如何恢复。本文以 Astro 生成的静态站点和 Cloudflare Workers Static Assets 为例，给出一套部署方案。文中的工作流是设计建议，并非已在示例项目中实施或验证的发布结果。

## 先确定部署边界

Astro 在构建时生成 HTML、脚本、样式和图片，Cloudflare Workers Static Assets 负责托管生成目录。对这种站点，发布物是生成后的 `dist`，不是整个源码仓库；在服务器上运行应用进程或数据库并不属于主站部署。[Cloudflare Static Assets 文档](https://developers.cloudflare.com/workers/static-assets/)说明了资源目录与 Worker 版本的关系。

若站点还使用独立的分析服务，例如自托管 Umami，它应有自己的服务部署、凭据、备份和回滚流程。更新静态站点不会更新分析服务。反过来，重启分析服务也不会改变已生成的页面。

推荐将流程拆成以下几个连续阶段：

```text
Pull Request 检查 → 合并到受保护的 main → 构建并校验 dist
                    → 保存与提交关联的产物 → 授权发布
                    → 检查真实域名 → 记录版本
```

## 一次构建，同一份产物发布

Pull Request 先执行类型检查、测试、内容与设计规则检查。生产构建在原生 CI runner 上执行，随后校验生成的页面：标题、canonical、站点地图、robots、404 页面、内部资源链接，以及生产环境应启用的脚本。生成文件通过检查后，保存为以提交 SHA 标识的短期构建产物。

发布作业下载**同一次工作流**生成的产物，再做一次只读校验，然后调用 Wrangler 发布。它不重新构建。这让检查对象与上线对象保持一致，也使发布失败时能够明确指向某个提交和产物。Node 版本、依赖锁文件、运行器镜像和 Actions 版本都应受控；使用 `npm ci` 安装锁定依赖，并将第三方 Action 固定到完整提交 SHA。[GitHub 工作流安全建议](https://docs.github.com/en/code-security/tutorials/secure-your-organization/protect-against-threats)解释了最小权限和 Action 固定版本的原因。

生产构建参数必须由 CI 明确提供。对于静态站点，搜索索引开关、统计脚本地址和公开网站 ID 等值可能直接写进 HTML；部署后设置 Worker 运行时变量，无法修改已经生成的页面。分析服务的地址和网站 ID 可以作为 GitHub Actions 变量管理，真正的访问令牌则放在 Secret 中。构建时检查必填值，并在 `dist` 中检查预期输出，避免一个“构建成功但统计消失”的版本上线。

## 把发布权限留在发布作业

CI 通过 Cloudflare API Token 和 Account ID 调用 Wrangler；交互式 `wrangler login` 适合开发者终端，不适合无人值守的工作流。给 Token 设置尽可能窄的账户和资源范围。部署已有 Worker 通常需要该 Worker 的 Editor 权限；如果同一次部署还要修改路由或自定义域名，则需要相应区域的 Workers Routes Write 权限。[Cloudflare GitHub Actions 指南](https://developers.cloudflare.com/workers/ci-cd/external-cicd/github-actions/)与[权限说明](https://developers.cloudflare.com/workers/authorization/)列出了认证方式和权限边界。

将 Cloudflare Token 放在生产发布作业可访问的 Secret 中。构建与测试作业不需要它。工作流的 `GITHUB_TOKEN` 只授予实际需要的权限，生产作业只接受受保护的主分支，并设置独立的并发组，避免两个发布同时改写线上版本。[GitHub 部署控制](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/control-deployments)提供了环境、分支与并发控制机制。

发布触发方式可以按团队节奏选择：如果合并到 `main` 就代表批准上线，可在合并后自动部署；如果需要固定发布窗口，可保留手动触发，并限制只能从 `main` 发布。这两种方式都应使用相同的检查、产物和线上验证步骤。私有仓库不要预设 GitHub Environment 的人工审核功能可用：其可用性随 GitHub 方案变化，应以[官方环境功能说明](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments)核对实际账户。

## 以真实域名判断发布结果

Wrangler 返回成功，只能证明部署请求完成。随后仍应从外部请求生产域名，至少验证：首页与代表性页面返回 200；不存在的路径返回真正的 404；HTML 引用的脚本和样式能够加载；HTTP 到 HTTPS 的跳转、canonical、robots 和站点地图正确；统计脚本与广告开关符合本次发布配置。把 Git 提交 SHA、工作流运行链接和 Cloudflare 部署版本记录在发布日志中。

若线上检查失败，应先确认故障范围，再将流量回退到上一稳定版本并重复线上检查。Cloudflare 支持通过 Wrangler 或控制台回滚 Worker 版本。[Cloudflare 回滚文档](https://developers.cloudflare.com/workers/versions-and-deployments/rollbacks/)也提醒：版本切换时，已打开的页面可能继续请求旧版资源。静态资源采用内容哈希文件名，必要时在新版本保留旧页面仍会请求的文件；对有复杂前端资源依赖的站点，还应评估[资源版本错配](https://developers.cloudflare.com/workers/versions-and-deployments/version-skew/)。

## 实施顺序

1. 补齐 CI 中的生产构建参数与产物校验，尤其检查会写入 HTML 的统计和索引配置。
2. 将现有“仅生成产物”的工作流扩展为独立发布作业；发布作业只下载、校验并上传同一份产物。
3. 创建限权 Cloudflare API Token，配置生产 Secret、分支限制与并发控制。
4. 先用手动触发完成一次端到端发布，记录提交、产物、部署版本和线上检查结果。
5. 流程稳定后，再决定是否改为合并 `main` 自动发布。

在 WSL 工作环境中，前端生产构建应交给允许构建的原生 CI runner；本地只运行不重新生成资源的检查。无论从哪里发起发布，完成标准都应是**真实域名上的目标版本通过验证**。

## 理解这套系统需要的网络知识

### 1. IP、端口与 DNS：地址和服务不是一回事

IP 用来找到网络接口，TCP 端口用来找到该接口上接听的程序。`[VPS1_PUBLIC_IP]:18443` 是 VPS1 的 nginx 入口，特斯拉真正的 HTTPS 服务一般在 443。把入口改成 18443，不会把加密变成明文，也不会要求 TeslaMate 使用 18443：这个端口只存在于两台 VPS 之间的一跳。

DNS 把域名转换成 IP。一般访问 `auth.tesla.cn` 会查到特斯拉的公网地址；这里 TeslaMate 所在的 Docker 网络为四个域名设置了本地网络别名，Docker 内置 DNS 因而返回中转地址。它只改变这个 Docker 网络内的解析，不改公网 DNS，也不是修改特斯拉域名所有权。

TeslaMate 的 `/etc/resolv.conf` 实际指向 `127.0.0.11`，这是 Docker 在自定义网络提供的内置 DNS。四个域名本次从 TeslaMate 内查询均返回 `172.20.0.9`。应用仍访问原来的 HTTPS 域名，没有改成代理 IP，也不需要理解 SOCKS。

有两次不同目的的解析：TeslaMate 查到“本地中转”，nginx 查到“真正的 Tesla”。所以 nginx 显式使用公网 DNS，不能再次用同一个网络别名解析目标，否则可能把请求转回自己，形成循环。当前 warp／relay 的系统 `resolv.conf` 已被 WARP 改成 `127.0.2.2`、`127.0.2.3`；nginx 的 `resolver` 指令仍明确指定 `1.1.1.1`、`1.0.0.1`，不依赖该系统文件。

### 2. TCP、TLS、SNI：不解密，为什么还能按域名转发？

TCP 先通过握手建立可靠字节流。TLS 再在这条字节流上握手：客户端发 ClientHello，通常用 **SNI** 告诉服务器“我要哪个域名”；服务器提供证书，客户端验证证书链及域名，然后协商加密密钥，传输加密的 HTTP 内容。

`ssl_preread` 只预读 TLS ClientHello，取出 SNI，**不终止 TLS**。它像看包裹外面的收件地址，不拆包。nginx 的 `map` 将四个许可域名映射到真实目标；遇到不在表里的域名就不给出可用目标。当前方案依赖传统可读 SNI，不承诺适用于隐藏目标名称的 ECH。

“TLS 端到端”不等于“只有一条 TCP 连接”：

- 架构 A：TeslaMate→VPS2 nginx、VPS2 nginx→VPS1 nginx、VPS1 nginx→Tesla 三段 TCP，代理复制字节；TLS 握手和加密会话的两端仍是 TeslaMate 与 Tesla。
- 架构 B：TeslaMate→nginx、nginx→Tesla 两段 TCP，后者的网络包再装进 WARP 隧道。

这些 nginx 配置没有 `listen ... ssl`，没有 `ssl_certificate`，也没有特斯拉私钥。DNS 指向代理不等于信任代理证书：TeslaMate 仍按原始域名验证特斯拉证书。只要不关闭校验、不植入额外受信任 CA，普通中转无法直接冒充特斯拉读取 token。本次 curl 未使用 `-k`，`ssl_verify_result=0`，说明测试请求的证书验证成功。

### 3. 四层代理、七层代理与 SOCKS 的区别

| 方式 | 在这里意味着什么 |
| --- | --- |
| 四层 TCP 代理 | nginx stream 转发字节；SNI 预读辅助选目标，不读取 HTTP 路径、Cookie 或 token |
| 七层 HTTP 代理／反向代理 | 理解 HTTP 方法、路径、请求头；若要看 HTTPS 内容，通常需终止 TLS |
| SOCKS5 | 客户端先按 SOCKS 协议告诉代理目标地址；nginx stream 的普通 `proxy_pass` 不会自动发这种握手 |
| 共享 WARP 网络 | nginx 像普通程序一样连目标；路由层决定把包送进隧道，无需 nginx 支持 SOCKS |

当前 GOST 的 SOCKS 仅绑定 `127.0.0.1:1080`，实际 Tesla 链路不通过它。nginx 没有填 `socks5://` 上游，而是连真正的 Tesla:443，由共享网络命名空间里的 WARP 接管出站路由。

### 4. Docker bridge、网络命名空间与 NAT

Linux 网络命名空间可以理解为一套独立的网卡、IP、路由、端口和防火墙视图。普通 bridge 容器各有自己的网络栈；host 模式直接使用宿主机网络栈；`network_mode: service:warp` 则让 relay 与 warp 共用同一套网络栈。

`traefik-teslamate_default` 虽然名字带 default，但它是 Compose 创建的自定义 bridge 网络，不是 Docker 的内置默认 bridge。本次网段为 `172.20.0.0/16`，网关 `172.20.0.1`；TeslaMate 为 `172.20.0.5`，warp 为 `172.20.0.9`。地址是快照，重建后可能变化，配置应依赖别名而不是写死这些地址。

共享网络意味着 nginx 的 443 就监听在 warp 的 `172.20.0.9` 上，relay 在 `docker inspect` 里没有自己的 Networks 是正常的。它们共享网络，不代表共享全部文件系统或进程命名空间。

NAT 是改写地址的机制。旧方案中，VPS2 bridge 容器访问公网通常经 Docker 的 SNAT/MASQUERADE，VPS1 看到来源为 VPS2 公网 IP；随后 VPS1 nginx 新建连接，特斯拉看到 VPS1 公网 IP。这并不是把原来的 TCP 包从 VPS2 原封不动路由到 Tesla，而是代理另建连接。

当前方案的隧道外层仍要经 VPS2 宿主机上网，但特斯拉面对的是 Cloudflare 的出口。仅把 DNS 换成 `1.1.1.1` 不会更换出口 IP；只有实际的数据转发路径改变才有用。

### 5. 路由、策略路由与 iptables

普通路由按目的 IP 找下一跳。策略路由则先由 `ip rule` 决定查哪张表，再在那张表里找路。只看 `ip route` 通常只看到 main 表，不能因此断言 WARP 没生效。

iptables 是 Linux 的包过滤／地址转换规则接口。filter 表的 INPUT 处理发给本机的包，FORWARD 处理经过本机转发的包，OUTPUT 处理本机发出的包；nat 表可做 DNAT、SNAT。链内顺序很重要，先匹配到的终止动作决定去留。`ACCEPT` 放行，`DROP` 静默丢弃，`REJECT` 则主动拒绝。

VPS1 用 host 网络，所以 18443 是宿主机本地监听，限制它用 INPUT 合理。如果是 Docker 发布端口，数据路径可能经过 DNAT 和 FORWARD，不能照搬“只在 INPUT 挡一下就行”的结论。IPv4 的 iptables 与 IPv6 的 ip6tables 也必须分别考虑。

### 6. WARP、WireGuard 与 MASQUE

WARP 是 Cloudflare 的客户端与网络服务，用加密隧道把流量送到 Cloudflare，再访问目标网站。WireGuard 是一种 VPN 协议；WARP 历史上使用过它，但 WARP 服务并不只支持这一种协议。

本机 `warp-cli settings` 的实测是 `WARP tunnel protocol: MASQUE`，`HTTP Version: MASQUE (HTTP/3 with HTTP/2 fallback)`。因此不能把这套部署描述成“已经搭了一条 WireGuard 隧道”，更不能虚构 `wg0`、WireGuard 私钥或 peer 配置。实际可见的接口叫 `CloudflareWARP`，隧道由官方 WARP 客户端维护。

Cloudflare 作为隧道出口能看到目标 IP、流量规模和部分连接元数据；传统 SNI 通常也可见。但这里没有开启 TLS 解密，应用层 HTTPS 内容仍加密。隧道加密和 HTTPS 是两层不同的保护，不能把“用了 VPN”理解成“所有参与方都看不到任何信息”。

### 7. closed、403、400、404：不同层的错误不要混着看

| 现象 | 可以说明什么／不能说明什么 |
| --- | --- |
| closed／connection refused／timeout | 连接层失败；可能是中转停了、端口没监听、网络丢包等，不是 HTTP 状态码 |
| 403 Forbidden | 服务端或前置防护拒绝请求；不自动等于 token 失效，也不能单凭它确定 IP 被哪条规则拦 |
| 400 Bad Request | 请求格式／参数不合要求；裸 OAuth authorize 缺少参数就是一种情形，不代表已登录 |
| 404 Not Found | 当前路径或资源不存在；可证明收到了某个 HTTP 服务的响应，不能证明账号权限正常 |
| 302 Found | 重定向，根路径常用于引导到登录流程；不等于登录成功 |
| 200 OK | 这一次请求成功；访问登录页 200 不等于 token 刷新或车辆 API 成功 |

## 架构 A：VPS2 → VPS1 → Tesla

```text
TeslaMate (VPS2)
  │  Docker DNS → 本地 relay:443
  ▼
VPS2 nginx relay :443
  │  TCP 段 2 · 公网 · TLS 字节仍加密
  ▼
VPS1 nginx SNI proxy :18443
  │  限制来源 + SNI 白名单
  ▼
Tesla HTTPS :443
  （看到 VPS1 出口 [VPS1_PUBLIC_IP]）
```

请求过程：

1. TeslaMate 请求 `https://auth.tesla.cn`；Docker DNS 返回旧 relay 在 tm 网络中的容器地址。旧地址没有在这次快照中复原，不在文中虚构。
2. TeslaMate 连 relay:443，发送带 `auth.tesla.cn` SNI 的 TLS ClientHello。VPS2 relay 不解析 SNI，只固定连 VPS1:18443 并转发字节。
3. VPS2 出站经宿主机 NAT，VPS1 INPUT 防火墙只允许 `[VPS2_PUBLIC_IP]` 访问 18443；nginx 再做一次来源检查。
4. VPS1 `ssl_preread` 读 SNI；在四个域名的白名单里，就通过公网 DNS 找真实 Tesla IP，再连其 443。
5. TLS 握手由 TeslaMate 与 Tesla 完成。登录后的加密 HTTP 请求、车辆 API 或长连接数据沿相同路径传输，响应按原连接返回。

旧 VPS2 relay 本身没有域名白名单，真正的 SNI 白名单与公网来源限制都在 VPS1。VPS1 目前已停止监听，但配置和 firewall 服务还在，不能把“服务 stopped”和“防火墙规则删掉了”混为一谈。

| external / name | 复用已经存在的 TeslaMate 网络，不由本项目新建该网络 |

| 配置项 | 逐项解释 |
| --- | --- |
| worker_processes / events | 一个 worker，每个 worker 的连接数上限为 256；代理也要用上游连接，不能简单理解为 256 个用户 |
| stream | 使用 TCP／UDP 流模块；此处 listen 未加 udp，所以是 TCP |

| listen 443 | 在容器网络里接 TCP 443，不是 VPS2 宿主公网开放 443 |
| proxy_connect_timeout 10s | 建立到 VPS1 的上游连接最多等 10 秒 |
| proxy_pass 固定 IP:端口 | 原样转发字节；不查 Tesla DNS，不处理 TLS，不添加 HTTP 头 |

### A4 · VPS1 nginx.conf

```nginx
worker_processes 1;
events { worker_connections 256; }
stream {
  resolver 1.1.1.1 8.8.8.8 valid=300s ipv6=off;
  map $ssl_preread_server_name $tesla_upstream {
    auth.tesla.cn                 auth.tesla.cn:443;
    auth.tesla.com                auth.tesla.com:443;
    owner-api.vn.cloud.tesla.cn   owner-api.vn.cloud.tesla.cn:443;
    streaming.vn.cloud.tesla.cn   streaming.vn.cloud.tesla.cn:443;
    default                       127.0.0.1:1;
  }
  log_format basic '$time_local $remote_addr $ssl_preread_server_name $status $bytes_sent $session_time';
  access_log /dev/stdout basic;
  error_log /dev/stderr warn;
  server {
    listen 18443;
    allow [VPS2_PUBLIC_IP];
    deny all;
    ssl_preread on;
    proxy_connect_timeout 10s;
    proxy_pass $tesla_upstream;
  }
}
```

| 配置项 | 逐项解释 |
| --- | --- |
| resolver ... valid=300s ipv6=off | 变量上游解析使用公共 DNS，覆盖缓存有效期为 300 秒，不查询上游 IPv6 地址 |
| map $ssl_preread_server_name | 从 ClientHello 的 SNI 生成上游地址变量 |
| 四条域名映射 | 只允许四个准确列出的名称，对应 Tesla 登录、车主 API 与流式服务；不是 `*.tesla.*` 全放行 |
| default 127.0.0.1:1 | 未匹配名称指向本地通常无人监听的 1 端口，不能访问任意公网目标；这是不可用目标兜底，不是 HTTP 拒绝页面 |
| 日志中的 SNI | 记录目标域名，不记录 HTTPS 请求体或 token |
| listen 18443 | 宿主机 TCP 入口，由 host 模式决定其网络位置 |
| allow ...; deny all | 按来源 IP 放行 VPS2，拒绝其余来源；这是网络来源限制，不是账号认证 |
| ssl_preread on | 读取 TLS 元数据而不终止 TLS |
| proxy_connect_timeout / proxy_pass | 限时建立真实上游连接，再转发 TLS 字节流 |

### A5 · VPS1 防火墙服务完整配置（公网地址已脱敏）

```ini
# <VPS1>/etc/systemd/system/tesla-egress-fw.service
[Unit]
Description=Allow only VPS2 to tcp/18443 (tesla egress)
After=network-online.target
[Service]
Type=oneshot
RemainAfterExit=yes
ExecStart=/bin/sh -c 'iptables -C INPUT -p tcp --dport 18443 -s [VPS2_PUBLIC_IP] -j ACCEPT 2>/dev/null || iptables -I INPUT 1 -p tcp --dport 18443 -s [VPS2_PUBLIC_IP] -j ACCEPT; iptables -C INPUT -p tcp --dport 18443 -j DROP 2>/dev/null || iptables -I INPUT 2 -p tcp --dport 18443 -j DROP; ip6tables -C INPUT -p tcp --dport 18443 -j DROP 2>/dev/null || ip6tables -I INPUT 1 -p tcp --dport 18443 -j DROP'
ExecStop=/bin/sh -c 'iptables -D INPUT -p tcp --dport 18443 -s [VPS2_PUBLIC_IP] -j ACCEPT; iptables -D INPUT -p tcp --dport 18443 -j DROP; ip6tables -D INPUT -p tcp --dport 18443 -j DROP; true'
[Install]
WantedBy=multi-user.target
```

| 配置项 | 逐项解释 |
| --- | --- |
| Unit / Description / After | 说明用途，并在 `network-online.target` 之后排序启动；After 本身不等于主动拉起该 target |
| Type=oneshot | 执行一次设置规则，不是后台常驻进程 |
| RemainAfterExit=yes | 命令退出后仍标记 active，所以 active 不等于有代理在监听 |
| iptables -C ... || -I | 先检查规则是否存在，缺少时再插入，减少重复添加 |
| INPUT 第 1 条 ACCEPT | 允许 VPS2 的 IPv4 来源访问 TCP 18443 |
| INPUT 第 2 条 DROP | 丢弃其他 IPv4 来源到 TCP 18443 的流量 |
| ip6tables DROP | IPv6 不设例外，拒绝 TCP 18443 |
| ExecStop 的 -D / true | 停止此单元会删除上述防火墙规则；true 让末尾退出码成功，不代表之前每项删除都成功 |
| WantedBy=multi-user.target | 供 `systemctl enable` 建立开机启动依赖；本次没有执行 enable／stop／start |

该服务直接在 ExecStart、ExecStop 中写 shell 命令，没有额外外部脚本需要展开。以下是本次读取的相关生效规则，不是让你执行的新增命令：

```text
IPv4（iptables -S 的相关行）
-A INPUT -s [VPS2_PUBLIC_IP]/32 -p tcp -m tcp --dport 18443 -j ACCEPT
-A INPUT -p tcp -m tcp --dport 18443 -j DROP

IPv6（ip6tables -S INPUT 的相关行）
-A INPUT -p tcp -m tcp --dport 18443 -j DROP
```

防火墙先挡住不需要的连接，nginx 再检查一次来源和 SNI，是两层限制。公网入口若必须保留，这比不加限制的 TCP 转发安全得多，但仍依赖 VPS2 IP 不变及规则顺序正确。

## 架构 B：VPS2 → WARP → Tesla

```text
TeslaMate 172.20.0.5
  │  Docker DNS → 四个 Tesla 别名
  ▼
warp + nginx 共享网络（172.20.0.9:443）
  │  nginx 读 SNI，新建真实 Tesla 上游连接
  ▼
CloudflareWARP 接口（策略路由表 65743；MASQUE 隧道）
  │  隧道外层经 VPS2 上网
  ▼
Cloudflare 出口 [WARP_EGRESS_IP]
  │  应用数据仍是加密 TLS
  ▼
Tesla HTTPS :443（不经过 VPS1）
```

请求过程：

1. TeslaMate 使用原来的四个 Tesla 域名。Docker 内置 DNS 现在把它们解析到 warp 的 `172.20.0.9`，因为别名已经从 relay 移到 warp。
2. relay 与 warp 共用网络。nginx 监听共享网络的 443，所以发往 `172.20.0.9:443` 的请求由 nginx 接收。
3. nginx 读取 SNI，检查四域名映射，并用显式公网 resolver 解析真实目标，避免再次解析到本地别名。
4. nginx 对真实 Tesla IP 发起连接。共享网络中的 `ip rule` 优先查询 WARP 路由表 65743，公共目标走 `CloudflareWARP`。
5. WARP 客户端通过 VPS2 的正常外网链路建立隧道；Cloudflare 解封装隧道并代为出站，Tesla 看到 Cloudflare IP。
6. 内网响应仍走 eth0 回 TeslaMate。WARP 的排除网段含 `172.16.0.0/12`，覆盖这里的 `172.20.0.0/16`，不会把容器间回包塞进公网隧道。

### 实际路由：main 表不变，流量为什么还是走 WARP？

```text
$ ip route
default via 172.20.0.1 dev eth0
172.20.0.0/16 dev eth0 proto kernel scope link src 172.20.0.9

$ ip rule
0:      from all lookup local
32765:  not from all fwmark 0x100cf lookup 65743
32766:  from all lookup main
32767:  from all lookup default

$ ip -4 route get 1.1.1.1
1.1.1.1 dev CloudflareWARP table 65743 src 172.16.0.2 uid 1000
    cache

$ ip -4 route get 172.20.0.5
172.20.0.5 dev eth0 src 172.20.0.9 uid 1000
    cache
```

上面命令在 warp 容器内执行，保留关键输出。优先级数字越小越先查；没有 `0x100cf` 标记的包先查 65743。表中有大量指向 `CloudflareWARP` 的公网网段；内网排除目标没有对应隧道路由，就继续查 main，走 eth0。fwmark 豁免机制用于让隧道自身等特定流量走正常路径，避免“隧道套自己”。本次没有逐包验证所有标记来源，不将每种进程行为写成定论。

这说明“让 nginx 走 WARP”不是把 VPS2 全局默认路由换掉，而是把 nginx 放进已具备 WARP 策略路由的那个网络命名空间。宿主机和其他普通容器不共享这一套策略，因而不必跟着更换出口。

### 出口验证：IPv4、IPv6 不要混看

```text
ip=[WARP_EGRESS_IP]
colo=LAX
loc=US
warp=on

$ warp-cli status

$ warp-cli settings  # 仅摘录非敏感相关行
(default) Mode: Warp

(api defaults) Exclude mode, with hosts/ips:

```

trace 这里只摘录关键字段。未加 `-4` 时，本次拿到的是 IPv6 出口；这不表示 IPv4 出口变了。nginx 设置 `ipv6=off`，其 Tesla 上游解析走 IPv4，所以这里用 `curl -4` 对齐验证。出口 IP 是本次快照，不是用户购买的固定独享地址。

当前生效文件在 `<VPS2>/data/traefik/applications/tesla-egress/`。运维说明 `WARP-OPERATIONS.md` 也已读取：它确认了四域名、共享网络、显式公共 DNS、无宿主发布端口以及回滚到旧“停止状态”的意图。`warp-data` 只保留路径，不展示内容。

| 配置项 | 逐项解释 |
| --- | --- |
| warp.image 的 @sha256 | 固定镜像内容摘要，避免同名标签后续漂移；摘要不是密码，可以公开。它不能证明镜像已通过安全审计 |
| restart: unless-stopped | 两服务都有重启策略，不等于业务可用性保证 |
| /dev/net/tun | 允许客户端创建／使用用户态隧道接口 |
| NET_ADMIN | 允许配置容器网络命名空间内的接口、路由等；这是较高权限 |
| MKNOD / AUDIT_WRITE | 分别允许特定设备节点操作及写内核审计日志；当前确实授予，本文没有验证它们能否安全移除 |
| disable_ipv6: 0 | 在该网络命名空间启用 IPv6；不代表 nginx 上游一定用 IPv6 |
| src_valid_mark: 1 | 让反向路径源地址校验考虑包标记，配合基于标记的策略路由 |
| WARP_SLEEP: '5' | 镜像启动等待参数；本次未审计镜像脚本，不据此推断完整重试或健康检查逻辑 |
| GOST_ARGS | SOCKS 监听只绑 `127.0.0.1:1080`；不是 nginx 的上游地址 |
| warp-data 持久化 | 保存 WARP 设备注册状态，可能含敏感材料；不打印、不公开、不加入普通文章附件 |
| warp.networks / aliases | 四个域名别名挂在 warp，不在 relay |
| relay 的只读与 tmpfs | 与旧 relay 相同，限定普通写入位置 |
| network_mode: service:warp | relay 使用 warp 的接口、IP、路由和端口空间；不是让 warp 充当另一个普通 TCP 上游 |
| depends_on / service_healthy | 启动时等 warp 健康；不是运行时持续保证，也不意味着 WARP 掉线就自动停止 nginx |
| 没有 ports／没有 privileged: true | 未映射宿主公网端口，inspect 也确认两容器均非 privileged；但 warp 仍有明确增加的权限 |

### B2 · 当前 nginx.conf

```nginx
worker_processes 1;
events { worker_connections 256; }
stream {
  log_format basic '$time_local $remote_addr $status $bytes_sent $session_time';
  access_log /dev/stdout basic;
  error_log /dev/stderr warn;
  resolver 1.1.1.1 1.0.0.1 valid=300s ipv6=off;
  resolver_timeout 5s;
  map $ssl_preread_server_name $tesla_upstream {
    default "";
    auth.tesla.cn auth.tesla.cn:443;
    auth.tesla.com auth.tesla.com:443;
    owner-api.vn.cloud.tesla.cn owner-api.vn.cloud.tesla.cn:443;
    streaming.vn.cloud.tesla.cn streaming.vn.cloud.tesla.cn:443;
  }
  server {
    listen 443;
    ssl_preread on;
    proxy_connect_timeout 10s;
    proxy_timeout 3600s;
    proxy_pass $tesla_upstream;
  }
}
```

| 配置项 | 逐项解释 |
| --- | --- |
| worker / events / 日志 | 与旧 VPS2 relay 相同；流日志的 `$status` 是 nginx stream 会话状态，不是上游 HTTP 403／200 |
| resolver 1.1.1.1 1.0.0.1 | 查询真实 Tesla 公网地址，绕开 Docker 本地域名别名；`valid=300s` 为缓存有效期设置 |
| ipv6=off | nginx 上游 DNS 不解析 IPv6 地址；容器自身的其他程序仍可用 IPv6 |
| resolver_timeout 5s | 解析上游名称最多等 5 秒 |
| map 与四条域名 | 按 SNI 选择四个明确的 Tesla:443 目标 |
| default 空字符串 | 未知 SNI 得不到有效上游，连接失败；不会返回自定义 HTTP 403 页面 |
| listen 443 / ssl_preread | 共享网络的 TCP 443 入口，预读 ClientHello，不终止 TLS |
| proxy_connect_timeout 10s | 上游 TCP 连接建立超时 |
| proxy_timeout 3600s | 相邻读写操作之间的超时，不是整条连接最多只能活一小时；适合较长流式会话 |
| proxy_pass $tesla_upstream | 连接真实域名目标；WARP 通过路由接管，不通过 SOCKS 接管 |

本次 `nginx -t` 通过。inspect 显示 warp 地址 `172.20.0.9`、网关 `172.20.0.1`、四个域名别名齐全；relay NetworkMode 为 `container:` 后接 warp 容器 ID，Networks 为空。这些运行态证据与 Compose 的设计一致。

为什么 relay 仍然必须运行？WARP 只提供出站网络，不会自动把四个域名的入站 443 请求转成正确的 Tesla 连接。nginx 负责接入、读取 SNI 和创建目标连接，WARP 负责它发出连接时的出口路径。停掉 relay 后，warp 别名仍在，TeslaMate 会继续连 `172.20.0.9:443`，通常遇到连接拒绝，而不是自动改用 VPS2 直连。

## 两种方案的取舍与安全边界

| 维度 | A：借 VPS1 | B：借 WARP |
| --- | --- | --- |
| 持续成本 | 依赖 VPS1；原套餐约 $48.77／年，另有运维成本 | 当前免费 WARP 使用方式；仍依赖 VPS2 及网络资源 |
| 时延 | 多一次 VPS2→VPS1 绕行 | 多一次隧道和 Cloudflare 出口路径；不保证更快，未做可比测速 |
| 故障依赖 | 两台 VPS、两层 nginx、公网 18443、防火墙 | VPS2、nginx、WARP 客户端、Cloudflare 网络 |
| 出口稳定性 | VPS1 公网 IP 通常较固定，续费及风控仍是变量 | 共享／可变化的 Cloudflare 出口，可能再次遇到风控 |
| 公网入口 | VPS1 18443，IPv4 仅放 VPS2，IPv6 丢弃 | Compose 不发布公网端口；同 Docker 网络仍可访问 |
| 容器权限 | VPS1 nginx 使用 host 网络 | warp 有 TUN、NET_ADMIN 等权限；nginx 共享其网络 |
| TLS 内容保护 | TeslaMate→Tesla 端到端 | 同样端到端，另加 WARP 隧道外层 |
| 新增信任 | VPS1 主机与镜像供应链 | 社区容器封装、官方 WARP 客户端及 Cloudflare 网络 |
| 当前状态 | VPS1 代理已停 | 正在使用；基础连通与证书测试通过 |

“没映射公网端口”不等于“只有 TeslaMate 能用”。同一 bridge 网络的其他容器、以及宿主机，通常可以访问容器 IP 的 443。当前 B 的 nginx 没有来源 IP allow／deny，主要限制是网络可达性和四域名 SNI 白名单。这个网络的 Internal 实测为 false，也不能把它称为严格隔绝外网的 internal 网络。

HTTPS 保护应用内容，但不能消除拒绝服务、流量分析、DNS 误导、客户端漏洞、容器逃逸或镜像供应链风险。固定 WARP digest 降低版本漂移风险，不等于审计结论；nginx 目前仍使用可变标签。本文未对 `caomingjun/warp` 源码、构建链或镜像逐层做安全审计。

> [!WARNING] 验证边界
> 当前证据只说明“WARP 正在工作，几个无凭据 HTTPS 测试绕过了此前的 403”。没有确认账号 token 刷新成功，也没有验证 WARP 断线时严格禁止直连的 kill switch。不要把健康检查和 `depends_on` 当成这种保证。

WARP 若异常，可能表现为连接失败，也可能因路由变化出现不同出口；需专门设计和测试才能承诺 fail-closed。本次没有做停机故障注入，也没有改防火墙来验证。未来如果需要更严隔离，应另行提出方案、先备份并获得同意，而不是趁写文章顺手更改。

## 按层排错：命令与判断方法

下面是供以后排错使用的只读命令清单，不是说每条都在本次运行过。尽量不装新工具、不新建临时容器；已有工具不存在就换容器里现成的工具。任何日志贴出来前，都要先确认不包含账号、token、请求头或敏感参数。

### 第一层：容器与 DNS

```bash
# 在 VPS2 上查看运行状态
cd <VPS2>/data/traefik/applications/tesla-egress
docker compose ps
docker inspect --format '{{.HostConfig.NetworkMode}}' tesla-egress-relay-1
docker inspect --format '{{json .NetworkSettings.Networks}}' tesla-egress-warp-1

# 从 TeslaMate 的真实环境查解析；本次可用的是 getent
docker exec traefik-teslamate-teslamate-1 cat /etc/resolv.conf
docker exec traefik-teslamate-teslamate-1 getent ahostsv4 auth.tesla.cn

# 有 dig / nslookup 的现成容器中才使用；无需为此安装
# dig @127.0.0.11 auth.tesla.cn A
# nslookup auth.tesla.cn 127.0.0.11
```

预期是 TeslaMate 用 `127.0.0.11`，四个名字返回 warp 当前容器地址。本次 TeslaMate 没有 nslookup，但 getent 可用。如果只在宿主机查询，看到公网地址并不能说明 Docker 别名失效，因为查询环境不同。

### 第二层：端口与路由

```bash
# VPS2：共享网络里应该看到 :443 与 localhost:1080
docker exec tesla-egress-warp-1 ss -lntp
docker exec tesla-egress-warp-1 ip -br addr
docker exec tesla-egress-warp-1 ip route
docker exec tesla-egress-warp-1 ip rule
docker exec tesla-egress-warp-1 ip -4 route show table 65743
docker exec tesla-egress-warp-1 ip -4 route get 1.1.1.1

# VPS1：当前旧中转已停，18443 无监听是符合现状的
ss -lntp 'sport = :18443'
systemctl cat tesla-egress-fw
iptables -S INPUT
ip6tables -S INPUT
```

连接拒绝常见于目标可达但没人监听；超时可能是 DROP 或链路不通。`ip route` 看着“正常直连”仍不足以下结论，要配合 `ip rule`、策略表、`route get` 和出口 trace。不要运行 `iptables -F`，也不要为排错删除规则。

### 第三层：WARP 出口与 TLS

```bash
# 在 VPS2，读取 WARP 状态与 IPv4 出口
docker exec tesla-egress-warp-1 warp-cli status
docker exec tesla-egress-warp-1 curl -4 -fsS --max-time 20 https://www.cloudflare.com/cdn-cgi/trace

# VPS2 宿主直连：只访问公开根路径，不带账号或 token
curl -4 -v --max-time 20 -o /dev/null https://auth.tesla.cn/

# 强制连当前中转地址，但保留域名对应的 SNI 与证书校验
# 172.20.0.9 是本文快照，地址变化后先查 inspect
docker exec tesla-egress-warp-1 curl -4 -v --max-time 20 --resolve auth.tesla.cn:443:172.20.0.9 -o /dev/null https://auth.tesla.cn/

# 在已有 openssl 的环境中：显式指定 SNI 和域名校验
openssl s_client -connect 172.20.0.9:443 -servername auth.tesla.cn -verify_hostname auth.tesla.cn -verify_return_error </dev/null
```

`curl --resolve` 只替换这一次连接的地址，URL 域名仍决定 SNI、HTTP 主机名和证书校验。openssl 的 `-servername` 提供 SNI，`-verify_hostname` 才明确要求验证对应主机名，二者不要混淆。工具存在且有可用 CA 信任库是这些命令的前提。

不要用 `curl -k` “证明问题解决”：它跳过证书验证。不要把 Authorization、Cookie、token 放进 `-v` 测试再粘贴输出。本次测试都是无凭据公开页面；真实登录应由用户在 TeslaMate 中完成，文章不收集任何凭据。

### 第四层：日志与 HTTP 结果

```bash
# 在 VPS2 项目目录，只读取所需服务和有限日志
docker compose logs --since 10m --tail 100 relay

# 旧架构如需核查 VPS1，仍只是读取已有日志
docker logs --since 10m --tail 100 tesla-egress-sni-proxy-1
```

nginx stream 日志中的 `$status=200` 只说明流代理会话在该层的处理情况。上游可能在加密的 HTTP 中返回了 403，nginx 看不到它。因此“nginx 日志有 200”不能证明登录成功，要在客户端观察真实 HTTP 响应及业务结果。流会话日志也常在会话结束时才出现，长连接尚未结束时暂时没有新 access log 不一定是没流量。

排错顺序建议：

1. 名字查错：先看 Docker DNS 与别名归属，不急着换 token。
2. 名字正确但连不上：看 nginx 是否监听、容器是否运行、旧架构 18443 的来源限制是否匹配。
3. WARP 显示 connected 但仍 403：核对请求是否真的经过 relay、是否是同一域名路径、实际 IPv4／IPv6 出口是谁。
4. 无凭据页面能通但登录失败：继续看 OAuth 参数、token 有效性、账号区域及客户端业务日志；网络放通只是前提。

## 回滚：恢复配置不等于恢复可用

本节只是操作说明，本次没有执行。变更前仍需重新确认目标，并把当时的 Compose、nginx、运维说明和必要状态备份到 `<VPS2>/root/backups` 或 `<VPS2>/data/backups`。`warp-data` 含注册材料，若需备份应单独保护权限，不随文章外传。

| 想恢复到什么状态 | 必须区分的动作 |
| --- | --- |
| 恢复迁移前的停止状态 | 停止当前 WARP／relay，恢复旧 VPS2 Compose 与 nginx 文件；不启动旧 relay，不启 VPS1 |
| 恢复旧架构 A 并实际可用 | 除恢复 VPS2 配置，还要确认 VPS1 出口仍通、18443 防火墙正确，再在两端启动对应服务 |
| 继续使用架构 B | 保留当前两服务和 warp-data；排查 WARP 或 nginx，不应只把 relay 停掉 |
| 完全取消任何中转，改回直连 | 需要消除／调整 Docker 别名并考虑 DNS 缓存；这不是“停 nginx”同一件事，且 VPS2 直连当前仍 403 |

`WARP-OPERATIONS.md` 中已记录下面这组恢复旧“停止状态”配置的命令。它们会停止服务并覆盖当前两个配置文件，只作原文引用；先完成新的备份、得到操作同意，再按实际目标执行：

```bash
docker compose stop
cp -a <VPS2>/root/backups/<tesla-egress-warp-backup>/tesla-egress/compose.yaml ./compose.yaml
cp -a <VPS2>/root/backups/<tesla-egress-warp-backup>/tesla-egress/nginx.conf ./nginx.conf
```

执行位置应是 `<VPS2>/data/traefik/applications/tesla-egress`。复制文件不会自动替换旧容器的运行配置；如果以后要启用 A，必须结合 Compose 容器重建及网络别名检查，避免保留的 warp 容器和新 relay 同时占用四个别名。仅执行 `docker compose start` 只能启动既有容器，不能保证其配置已切回 A。

VPS1 原服务已存在时，在其 `<VPS1>/data/traefik/applications/tesla-egress` 执行 `docker compose start` 可重新启动旧代理；但这属于恢复对外服务，不是本文的只读核查。要先确认用户确实要回到 A，而不是仅保存旧配置。也不要为了停 nginx 去停 `tesla-egress-fw`：停该 systemd 单元会删除防火墙限制。

运维说明还记录了 B 的启动／更新命令 `docker compose up -d --wait --wait-timeout 120`。它是有状态操作，不在本次执行。共享网络场景下，如果 warp 被重建，要一起核查 relay 是否仍共享正确的新网络命名空间；“两个容器都显示 Up”并不足够。旧容器和注册数据可以保留，不需要为了回滚删除任何东西。

## 资料来源与学习顺序

建议学习顺序：

1. 先练 DNS：从 TeslaMate 内 `getent` 看域名，再比较宿主机解析。理解为什么同一个域名在两个环境返回不同地址。
2. 再练 TCP／TLS：用 `curl --resolve` 指定中转 IP，仍用真实域名校验证书；理解连接地址与 TLS 身份并不相同。
3. 再看 Docker：比较 host、bridge、`service:warp` 三种模式，找到每一段连接由哪个网络栈发出。
4. 最后看策略路由和防火墙：用 `ip rule` + `route get` 解释出站，用 INPUT 规则解释旧公网入口；不要靠删规则来试错。

服务器一手来源：VPS2 迁移前备份中的 `compose.yaml`、`nginx.conf`；VPS1 现存的同名文件、`systemctl cat tesla-egress-fw`、相关 iptables／ip6tables 规则；VPS2 当前 `compose.yaml`、`nginx.conf`、`WARP-OPERATIONS.md`，以及选择性 Docker inspect、DNS、接口、路由、WARP 状态和无凭据 HTTPS 探测。没有读取数据库、Tesla token、rclone 凭据或 warp-data。本文配置范围完整，设备注册身份材料刻意不包含在内，因此不是可迁移账号身份的全盘备份。

从两级 Git 同步理解 CI/CD：AstroPaper 主题更新与博客发布

Updated: 13 Oct, 2026
| Edit page

AI 生成内容（AI-generated content）：本文由 AI 生成。

一个基于开源主题的博客，往往需要同时维护三类内容：上游主题代码、本站定制和持续新增的文章。更新主题时，既要接收上游修复，也要保留站点配置和文章，最后还要确认网站可以正常生成。

本文以 AstroPaper 原仓库 satnaing/astro-paper、它的 fork byodian/astro-paper 和博客主仓库 byodian/all-in-github 为例，解释这套自动化如何工作。分析对应 2026-10-13 的实现：主题仓库提交 0c642f2，主仓库提交 625992e。

一条分成两级的更新链路

主仓库通过 Git subtree 将 fork 的主题源码放进 blog/，文章也存放在这个目录下。完整链路如下：

satnaing/astro-paper/main
    │
    │ 每月 25 日：普通 merge → 验证 → 自动推送
    ▼
byodian/astro-paper/dev
    │
    │ 每月 1 日：subtree merge → 验证 → 创建或更新 PR
    ▼
all-in-github 的同步 PR
    │
    │ 人工检查，通过 merge commit 合并
    ▼
all-in-github/main 的 blog/
    │
    │ main 更新：生成静态网站 → 发布产物
    ▼
GitHub Pages

两级同步分别解决不同的问题：主题 fork 接收上游源码，主仓库接收已经整合本站定制的主题。文章始终由主仓库维护。

环节来源目标合并方式成功后的操作
上游同步上游 mainfork 的 dev普通 Git merge自动推送 dev
博客同步fork 的 dev主仓库 blog/Git subtree merge创建或更新 PR
网站发布主仓库 mainGitHub Pages生成并发布静态文件更新线上网站

两个同步工作流独立调度。fork 更新不会立即触发主仓库同步；需要等待主仓库的定时任务，或手动运行 Sync blog theme。上游同步跟踪的是 main 最新提交，范围包括尚未发布为正式版本的改动。

主题 fork 如何自动合并上游

实现位于主题仓库的 sync-upstream.yml、sync-upstream.mjs 和 upstream.config.json。

工作流先执行同步测试。实际更新任务通过 needs: test 等待测试成功，仅在定时或手动触发时运行；修改工具代码产生的 push、PR 事件只运行测试。

同步脚本的入口是：

- name: Prepare upstream merge
  id: prepare
  run: node scripts/sync-upstream.mjs --base-ref origin/dev.github/workflows/sync-upstream.yml

固定输入版本，判断是否已经同步

脚本先将 origin/dev 解析为 fork 基线 SHA，再执行 git fetch 获取上游 main，读取 FETCH_HEAD 对应的提交。

这样，本次运行处理的是两个确定版本。即使远端分支在验证期间继续前进，也不会改变这次合并的输入。

接着执行：

git merge-base --is-ancestor <上游SHA> <fork基线SHA>

如果上游提交已经是 fork 的祖先，就说明这个版本已经合并，直接退出。判断依据是 Git 历史关系，而非比较两个分支当前的文件是否相同。

在独立 worktree 中合并

有更新时，脚本创建新分支和 worktree。worktree 是同一 Git 仓库的另一个检出目录，共享对象数据库，但有自己的分支、工作区和暂存区。

合并在新目录中进行，原工作目录中的分支和未提交内容不会被切换或覆盖：

git merge --no-ff --no-commit <上游SHA>

--no-ff 保留合并节点，--no-commit 留出提交前的处理机会。此时可以恢复本站内容，再判断是否还存在需要人工解决的源码冲突。

按路径保留本站内容

配置中的受保护路径包括文章、站点配置、About、favicon、默认 OG 图片以及本地字体。脚本从 fork 基线恢复这些内容，并通过 Git 差异检查确认一致。

这一步无论是否发生冲突都会执行。原因是 Git 自动合并成功只能说明文本合并没有冲突，不能说明上游修改符合本站需求。例如，上游新增的示例文章可以被正常合并，但本站并不需要发布它。

对于基线不存在的受保护路径，脚本移除本次上游引入的文件。其余源码走普通合并；如果仍有冲突，停止处理并保留现场，不自动选择任意一侧。

验证成功后才更新远端

准备脚本完成合并提交并生成同步记录，但不自行执行验证或推送。验证由后续工作流步骤负责，包括冻结锁文件安装、Astro 检查、ESLint、Prettier、生产构建和 Pagefind 索引生成。

工作流还会再次检查受保护路径，并确认验证没有意外修改已跟踪文件，或新增非忽略文件。

全部通过后，才执行：

git -C "$SYNC_WORKTREE" push origin HEAD:refs/heads/dev

这里使用普通 push。如果验证期间远端 dev 出现其他新提交，导致本次更新不再是快进推送，Git 会拒绝更新。工作流不会覆盖这些新提交，需要重新运行同步。

冲突、检查失败或推送失败时，CI 上传包含 Git 历史、源码、patch 和状态信息的恢复包，保留 14 天。远端 dev 不会收到失败的合并结果。

主仓库如何接收 subtree 更新

实现位于主仓库的 sync-blog.yml、blog.mjs 和 blog.config.json。

工作流每月 1 日运行，也支持手动触发。主仓库文章更新时，它会再次检查主题来源并刷新尚未合并的同步 PR。

关键命令是：

npm run blog:sync -- --base-ref origin/main --prepare-only

package.json 将 blog:sync 映射到 node scripts/blog.mjs sync。-- 后的参数传给脚本；--prepare-only 将合并准备和后续验证分开，避免重复执行检查。

从 subtree 记录判断版本

脚本通过 sourceCommit() 查找提交信息中的 git-subtree-dir: blog 和 git-subtree-split:，读取上一次接收的主题 SHA。

再拉取 fork 的 dev，固定本次主题 SHA。如果与记录一致，就不创建分支或 PR。

这与主题 fork 的祖先判断不同：fork 使用完整 merge 历史识别已经合并的上游；主仓库通过 subtree 元数据识别已经接收的主题版本。

将主题根目录映射到 blog/

有更新时，脚本基于主仓库基线建立独立 worktree，然后执行：

git subtree merge --prefix=blog <主题SHA> --squash

普通 merge 对应仓库根目录之间的合并；这里的 subtree merge 将主题仓库根目录对应到主仓库的 blog/。

--squash 将来源侧的更新汇总为一次 subtree 更新，仍记录对应主题 SHA。它与 PR 的 Squash 合并是两个不同操作：同步 PR 需要通过 Create a merge commit 合并，以保留同步所依赖的历史关系。

主仓库文章始终按主仓库基线恢复

subtree 合并后，脚本始终恢复整个 blog/src/content/blog/，并验证文章的路径和内容一致。

因此，上游主题的示例文章、删除、改名，以及自动合并的正文修改都不会进入最终结果。源码冲突则仍需人工处理。

验证通过后，工作流推送专用分支 automation/sync-blog，使用 gh pr create 或 gh pr edit 创建、更新同一个 PR。

该分支每次会基于最新 main 重新生成，所以推送使用带预期 SHA 的 --force-with-lease。它只替换专用自动化分支；主分支仍通过人工合并 PR 更新。

GitHub Actions 如何执行 shell 命令

GitHub Actions 将执行过程分成三个层次：

层次作用
WorkflowYAML 定义触发条件、权限、任务和执行关系
Job分配给 runner 执行的一组工作
Step执行一段命令，或调用一个现成 action

runs-on: ubuntu-latest 选择 GitHub 托管的 Ubuntu 执行环境。当前同步任务没有配置容器，命令在 runner 的操作系统环境中运行。uses: 调用现成 action，run: 执行命令。参见 GitHub 工作流说明。

YAML 安排执行，runner 启动进程

对于多行 run，runner 将内容写入临时脚本文件，再启动 shell 执行。当前 Ubuntu 工作流没有显式指定 shell，默认执行形式是：

bash -e <临时脚本文件>

显式指定 shell: bash 时，GitHub 使用包含 -eo pipefail 的另一组参数。因此默认执行形式和显式指定 Bash 并不完全相同。参见 GitHub shell 执行规则。

一次 run 中的多行命令共用同一个 shell；不同 run 步骤会启动新的 shell。同一个 job 中的文件会保留，但前一步的 cd 或普通 shell 变量不会自动延续到下一步。

不同 job 也不会自动共享工作目录。主题仓库的测试 job 和同步 job 都需要各自 checkout；needs: test 表达等待测试成功，不表示同步 job 可以直接使用测试 job 的文件。

Shell 再调用 npm、Node.js 和 Git

主题仓库的进程调用关系是：

GitHub runner
    → Bash
        → node scripts/sync-upstream.mjs
            → Git 子进程

主仓库多经过 npm 的命令入口：

Bash
    → npm run blog:sync
        → Node.js 同步脚本
            → Git 子进程

npm 读取 package.json 中的脚本定义，通过 shell 执行对应命令。参见 npm 脚本机制。

主题脚本内部使用 spawnSync 启动 Git，主仓库使用 cross-spawn 的 cross-spawn.sync 适配跨平台进程启动。例如：

spawnSync("git", ["fetch", "--no-tags", repository, sourceRef], {
  cwd,
  encoding: "utf8",
});

这类调用分别传入程序名称和参数，没有启用 shell 字符串解释。Node 等待 Git 结束，再读取退出状态和输出，决定继续执行还是终止。参见 Node.js 子进程说明。

步骤之间如何传递数据和失败状态

用 GITHUB_OUTPUT 传递结果

同步脚本向 $GITHUB_OUTPUT 指向的文件写入键值：

changed=true
source=<来源SHA>
base=<基线SHA>
worktree=<工作目录>

runner 读取后，后续步骤通过 id: prepare 引用这些结果：

if: steps.prepare.outputs.changed == 'true'
env:
  SYNC_WORKTREE: ${{ steps.prepare.outputs.worktree }}

${{ ... }} 属于 Actions 表达式，用来设置执行条件和环境；命令里的 $SYNC_WORKTREE 再由 Bash 展开。参见 步骤输出机制。

用退出码决定是否继续

进程退出码 0 表示成功，非零表示失败。只向终端打印“发生错误”，但最后仍以 0 退出，不能可靠地阻止后续发布。

两个同步脚本都会检查子进程状态；不能继续时抛出错误，最终让 Node 以非零状态退出。工作流据此阻止普通后续步骤，配置了 if: failure() 的步骤则保存失败现场。参见 GitHub 退出码规则。

脚本也有需要主动解释的非零状态。例如，merge-base --is-ancestor 的返回值 1 表示来源尚未合并，是进入同步流程的正常分支；Git merge 的非零状态则可能表示冲突，需要恢复受保护内容后再次检查。这些判断由脚本处理。

权限让命令能够写回仓库

生成合并提交只修改 runner 上的临时仓库。只有 push 成功，远端分支才真正更新。

两个工作流通过 GITHUB_TOKEN 和声明的权限执行写入：主题同步需要 contents: write；主仓库同步还需要 pull-requests: write，才能创建和更新 PR。Git 提交中的作者身份与执行远端写入的认证是两件不同的事。

CI/CD 的本质与网站发布

手动更新主题，需要选择版本、获取代码、合并、保留本站内容、检查和推送。CI/CD 把这些操作转化为版本化的规则，由事件驱动执行，并保存日志、退出状态和产物。

在这套实现中，YAML 负责执行安排，脚本负责项目规则，Git 负责版本关系，检查工具提供是否可以继续的证据。

概念含义本项目中的对应行为
持续集成，CI反复验证代码集成后的结果同步测试、类型检查、Lint、格式检查和构建
持续交付自动准备经过验证、可合并或发布的结果，允许人工决定落地主仓库生成同步 PR，由人工合并
持续部署满足条件后自动发布主仓库 main 更新后自动生成并发布网站

主仓库的 deploy.yml 监听 main 的 push，安装博客依赖、生成 blog/dist，然后使用 peaceiris/actions-gh-pages 将静态产物发布到 gh-pages，供 GitHub Pages 提供网站。

源码同步和网站部署有不同职责：同步任务准备经过验证的主题版本，部署任务生成并发布网站。当前主仓库仍保留人工合并同步 PR 的环节，因此不能把整条链路描述为完全无人介入的更新流程。

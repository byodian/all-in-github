工具集合站如何兼顾独立项目、SEO 与 Google AdSense

10 Oct, 2026
| Edit page

AI 生成内容（AI-generated content）：本文由 AI 生成。

一个工具集合站需要同时解决三件事：让用户发现工具，让各个工具独立迭代，以及让后续的广告接入保持可维护。主站应承担工具目录、使用指南和品牌入口的职责，各工具继续独立开发和部署；公开内容使用静态生成或服务端渲染，广告按页面用途配置。

本文基于现有项目检查与 Google、Astro 官方文档调查。下文明确区分已观察到的事实、平台要求和架构建议；主站尚未实现，域名示例仅用于说明设计。

项目现状与目标

当前工作区包含两个工具，父目录本身没有 Git 仓库，工具目录各自保存 Git 历史。

工具技术与数据存储维护重点
bookmarks原生 HTML、CSS、JavaScript；浏览器 IndexedDB导入导出、数据格式兼容、浏览器交互
textdiffNext.js、React、Prisma；SQLite编辑器交互、接口、数据库迁移和备份

其中 bookmarks 已发布到独立 GitHub 仓库。其纯静态架构和浏览器存储设计可以从固定提交的项目说明查证。代码推送成功与线上网站部署成功是两个独立状态。

新增目标是：主站集合全部工具，各工具后续接入 Google AdSense，主站具备可持续经营的 SEO 能力。这里的“集合”首先意味着统一发现入口和内容组织，并不要求所有工具使用同一种框架或同一个运行进程。

主站与工具如何划分职责

建议新增独立的 portal 项目，与现有工具并列维护：

apps/
├── docs/                 # 集合站规划与跨项目约定
├── portal/               # 主站，独立仓库
│   ├── docs/             # 开发、部署与维护文档
│   └── src/              # 工具目录、公开介绍和指南
├── bookmarks/            # 书签工具，独立仓库
└── textdiff/             # 文本工具，独立仓库

主站负责首页、分类、工具介绍、教程、关于页面和隐私说明。工具项目负责实际功能、运行环境和数据生命周期。工具详情页用普通链接进入应用；初期无需通过 iframe 承载所有工具，也无需让主站加载编辑器、数据库客户端等工具运行依赖。

对于以目录和文章为主的 portal，我建议优先考虑 Astro，主要内容生成 HTML，仅对搜索、筛选等交互加载 JavaScript。这与其官方描述的 Islands 架构一致。Astro 官方文档

Next.js 的静态生成或服务端渲染也能满足需求。选择 Astro 是基于当前主站的内容性质和维护成本，不意味着某个框架天然获得更高排名。

域名组织与独立部署

建议先采用“主域名放公共内容，子域名运行独立应用”的结构：

地址示例页面职责
example.com/品牌与工具总入口
example.com/tools/bookmarks/书签工具介绍、限制、使用方法
example.com/tools/textdiff/文本比较工具介绍与示例
example.com/guides/import-browser-bookmarks/浏览器书签导入教程
bookmarks.example.com/书签应用
textdiff.example.com/编辑与比较应用

这样可以让静态工具和带数据库的工具分别选择合适的部署环境，同时在主站持续维护公开内容。如果未来希望工具直接运行在主域名路径下，也可以采用按路径路由的方式，但需要处理资源路径、应用路由和代理配置。

这是维护上的取舍。Google 的 SEO 入门指南允许按业务需要选择子域名或子目录，不能据此声称某种地址结构必然排名更好。Google SEO 入门指南

域名和主要 URL 应尽早稳定。正式域名上线后，再处理旧部署地址的跳转或重复内容归一化；不能把所有工具页面的 canonical 都指向主站首页。

SEO：为每个工具建立真实的搜索入口

主站除了提供工具卡片，还应为每个已上线工具提供可独立阅读的公开页面。页面回答用户的具体问题：工具解决什么问题、怎样使用、支持哪些格式、数据保存在何处，以及有哪些限制。

例如书签工具可以展示浏览器导出文件的导入步骤和备份方法；文本比较工具可以展示公开示例，解释差异标记及常见操作。指南围绕真实功能编写，避免为了覆盖关键词批量生成只有名称不同的页面。

建议把下面几项作为主站的技术验收条件：

  1. 首次 HTML 响应包含主要标题、工具说明和可访问的链接。
  2. 每个公开页面拥有明确且独立的 title、description 和稳定 URL。
  3. 导航使用可抓取的链接；工具详情、分类和指南之间建立合理关联。
  4. sitemap 包含准备收录的规范页面，错误 URL 返回真实的错误状态。
  5. 多个地址出现相同内容时，明确规范地址；不同用途的页面各自保留身份。

Google 可以执行 JavaScript，但官方仍建议考虑服务端渲染或预渲染，因为它有利于用户和抓取程序获得内容。标题、描述和 canonical 也应保持一致。Google JavaScript SEO 文档

sitemap 帮助搜索引擎发现页面，但提交 sitemap 不等于保证收录。上线后需要用 Search Console 观察实际抓取和索引情况。Google sitemap 文档

结构化数据应表达页面实际存在的信息，例如面包屑或文章信息。不要编造评价、评分或其他不可见内容；标记正确也不保证搜索结果展示富媒体效果。Google 结构化数据要求

公开说明与用户数据分开处理

工具的公开介绍、教程和演示适合作为搜索入口。个人书签、草稿、文档历史和工作区内容应按其数据用途保护，不应成为默认公开的索引对象。

对于确实公开访问、但不希望收录的页面，可以使用 noindex。Google 必须能够抓取页面才能看到该规则，因此不要同时用 robots.txt 阻止抓取，再期待页面内的 noindex 生效。Google noindex 文档

noindex 只处理搜索收录，不能承担访问控制职责。含私人数据的服务端资源仍需要相应的权限控制；对于浏览器本地数据，也应避免将内容写入公开 URL、统计事件或广告参数。这是实现时需要落实的数据边界，本文没有对现有工具完成安全审计。

AdSense：统一账号，各工具配置自己的广告单元

每个工具接入 AdSense，并不意味着每个工具都要注册一个账号。AdSense 通常只允许每个发布商拥有一个账号，可在该账号中管理多个站点。AdSense 账号说明

按 Google 当前公开的站点管理规则，普通子域名不再作为所属站点之外的独立条目管理；可添加的站点类型包括独立域名和特定平台的子域名。因此域名规划应与站点管理方式一起考虑，各工具可以通过不同广告单元区分投放与收益。AdSense 站点管理说明

同一账号不意味着所有页面都适合展示广告。Google 要求独特、相关的内容和良好的体验，也明确提醒不要在缺乏原创内容的页面放置广告。对工具站的具体建议是：先完成可用工具、实用说明和真实指南，再申请审核；不能把加入广告代码当作获批条件。AdSense 页面准备要求、内容质量说明

建议统一管理 publisher ID，让每个工具单独维护广告单元 ID、投放位置与启用开关。尚未取得真实账号配置时保持广告关闭，不填入虚构 ID。正式接入时按照账号提供的信息维护 ads.txt；若子域名使用不同的卖方配置，再按官方规则声明子域名。AdSense ads.txt 说明

广告位置、性能与隐私说明

工具页通常有密集的点击和键盘操作。建议先在公开说明或指南区域设置少量广告，预留容器空间，再评估应用页面的合适位置。

广告不要贴近导入、下载、复制、保存、删除或导航按钮，也不要伪装成工具操作。Google 的投放政策明确要求避免引导误点。AdSense 广告位置政策

预留广告空间既能减少误点，也能减少页面布局变化。性能目标可参考 LCP 约 2.5 秒以内、INP 约 200 毫秒以内、CLS 约 0.1 以内；这些是体验目标，需要在广告启用后结合真实用户数据验证，不能只看无广告的本地页面。Google Core Web Vitals 文档

接入广告后，应更新工具的隐私描述。可以准确说明“书签内容保存在本地”，但不应笼统承诺整个网站完全没有第三方请求。隐私政策需要披露 Google 等第三方的广告 Cookie、用途和退出方式。AdSense 隐私说明要求

向欧洲经济区、英国和瑞士用户提供个性化广告时，Google 要求使用经过认证、集成 IAB TCF 的同意管理平台。接入时应按实际受众和投放方式配置。Google 同意管理要求

后续怎样持续维护

主站维护一份工具登记数据，至少包括稳定标识、名称、分类、摘要、应用地址、仓库地址和上线状态。页面模板负责展示，工具登记数据负责入口信息，指南正文负责详细内容。新增工具时登记一次，再补充其专属说明和真实使用示例。

各工具继续独立提交、检查和部署。先共享品牌约定、文档模板和广告配置原则，等出现实际重复代码时再提取公共模块。当前只有两个技术栈不同的工具，没有必要立即引入复杂的跨仓库依赖体系。

数据维护仍然是工具项目自身的责任：书签应用验证导出文件可以恢复；SQLite 应用明确数据库文件的持久化位置，并验证备份恢复。现有文本工具还需要规划可审查的数据库迁移，把数据库变更与前端编译分离。Prisma 官方将 db push 定位为适合快速原型迭代的方式，它不会生成迁移历史。Prisma 原型与迁移说明

实施顺序与验证范围

建议按下面顺序实施，减少后期改域名、改路由和重写内容的成本：

  1. 确定品牌、主域名、首发语言和独立工具的地址规则。
  2. 创建 portal，完成首页、两个工具详情页及必要的关于、联系和隐私页面。
  3. 落实 HTML 内容、元数据、规范地址、sitemap 和错误页面。
  4. 发布主站和工具，配置 Search Console，并验证公开页面抓取情况。
  5. 增加真实指南，观察搜索词、工具使用和移动端体验。
  6. 完成 AdSense 审核和真实配置，在合适页面逐步启用广告。

本次已完成目录、技术栈、Git 仓库边界和部分配置检查，并查阅相关官方文档。bookmarks 代码已推送，其 JavaScript 语法检查通过。由于当前环境为 WSL，本地没有执行前端构建。

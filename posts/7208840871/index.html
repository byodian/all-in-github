WSL 2 报错 Exec format error 无法运行宿主机 .exe 的根因与修复

27 Nov, 2026
| Edit page

AI 生成内容（AI-generated content）：本文由 AI 生成。

在开启了 systemd=true 的 WSL 2（Ubuntu 24.04，WSL 2.7.3.0）中执行 code . 或 cmd.exe 时，终端报错 Code.exe: Exec format error，所有 Windows 宿主机 .exe 程序均无法启动。排查表明，Ubuntu 实例单独关机重启时，systemd-shutdown 调用 disable_binfmt() 清空了内核 binfmt_misc 中的 WSLInterop 注册项；重新启动实例时，Ubuntu wsl-setup 包自带的 ConditionVirtualization=!wsl 又拦截了 systemd-binfmt.service，导致 WSL 生成的恢复钩子未能执行。在 /etc 下补充 binfmt.d 配置并清空该条件限制，重启 systemd-binfmt.service 即可恢复并防止复发。

故障现象与报错入口

在 WSL 终端运行 code 命令时，Shell 报错如下（用户名与主机名已脱敏）：

/mnt/c/Users/<user>/AppData/Local/Programs/Microsoft VS Code/bin/code: 62: /mnt/c/Users/<user>/AppData/Local/Programs/Microsoft VS Code/Code.exe: Exec format error

报错脚本对应 VS Code 的 WSL 启动包装器 resources/win32/bin/code.sh。该脚本在检测到 $WSL_DISTRO_NAME 后原本会先调用一次 Code.exe 来定位 ms-vscode-remote.remote-wsl 扩展路径：

ELECTRON_RUN_AS_NODE=1 "$ELECTRON" "$CLI" --locate-extension $WSL_EXT_ID >/tmp/remote-wsl-loc.txt 2>/dev/null </dev/null
WSL_EXT_WLOC=$(cat /tmp/remote-wsl-loc.txt)

if [ -n "$WSL_EXT_WLOC" ]; then
	WSL_CODE=$(wslpath -u "${WSL_EXT_WLOC%%[[:cntrl:]]}")/scripts/wslCode.sh
	"$WSL_CODE" "$COMMIT" "$QUALITY" "$ELECTRON" "$APP_NAME" "$SERVERDATAFOLDER" "$@"
	exit $?
fi
# ...
ELECTRON_RUN_AS_NODE=1 "$ELECTRON" "$CLI" "$@"
exit $?resources/win32/bin/code.sh

第一次调用 Code.exe 因为带有 2>/dev/null，执行失败后没有输出错误，WSL_EXT_WLOC 为空；脚本随后回退到末尾直接运行 "$ELECTRON"（即 Code.exe），才把内核返回的 ENOEXEC（Exec format error）打印到终端。此时直接执行 /mnt/c/WINDOWS/system32/cmd.exe 也会触发同样的错误，说明问题出在 WSL 跨系统执行链路本身。

现场排查证据

WSL 运行宿主机 .exe 依赖两部分基础设施：一是 /run/WSL/*_interop Unix Socket 通信通道（由环境变量 $WSL_INTEROP 指向），二是 Linux 内核 binfmt_misc 文件系统中的 WSLInterop 规则，用于把文件头魔数为 MZ（0x4d 0x5a）的 Windows PE 可执行文件交给 WSL 的 /init 进程转发执行。

检查现场环境状态：

$ env | grep WSL_INTEROP
WSL_INTEROP=/run/WSL/6612_interop

$ ls -la /run/WSL/
lrwxrwxrwx 1 root root 18 Nov 27 09:32 1_interop -> /run/WSL/2_interop
srwxrwxrwx 1 root root  0 Nov 27 09:32 2_interop
srwxrwxrwx 1 root root  0 Nov 27 10:29 6612_interop

$ ls -la /proc/sys/fs/binfmt_misc/
--w------- 1 root root 0 Nov 27 09:32 register
-rw-r--r-- 1 root root 0 Nov 27 09:32 status

$ cat /proc/sys/fs/binfmt_misc/status
enabled

Socket 通道正常存在，binfmt_misc 文件系统也处于 enabled 状态，但目录下没有任何已注册的二进制格式条目，WSLInterop 已经消失。内核遇到 MZ 开头的 PE 文件时找不到对应的解释器，直接返回 Exec format error。

继续检查 systemd-binfmt.service 的合并单元配置与运行状态：

# /usr/lib/systemd/system/systemd-binfmt.service
[Service]
Type=oneshot
RemainAfterExit=yes
ExecStart=/usr/lib/systemd/systemd-binfmt
ExecStop=/usr/lib/systemd/systemd-binfmt --unregister

# /run/systemd/generator/systemd-binfmt.service.d/override.conf
[Service]
ExecStop=
ExecStart=/bin/sh -c '(echo -1 > /proc/sys/fs/binfmt_misc/WSLInterop) ; (echo ":WSLInterop:M::MZ::/init:P" > /proc/sys/fs/binfmt_misc/register)'

# /usr/lib/systemd/system/systemd-binfmt.service.d/wsl.conf
[Unit]
ConditionVirtualization=!wsl systemd-binfmt.service

systemctl status systemd-binfmt.service 显示该服务在启动时被跳过：

Condition: start condition unmet at Fri 2026-11-27 09:32:31 CST
           └─ ConditionVirtualization=!wsl was not met

再对照 journalctl 在 09:32:01 到 09:32:32 之间的日志，可以看到 WSLInterop 从正常到失效的完整时间线：

09:32:01 kernel: Run /init as init process (WSL version 2.7.3.0)
09:32:02 wsl-pro-service[191]: WARNING ... could not read agent port file "/mnt/c/Users/<user>/.ubuntupro/.address": no such file or directory
09:32:19 systemd-logind[187]: System is powering down.
09:32:20 systemd[1]: Reached target poweroff.target - System Power Off.
09:32:31 systemd[1]: systemd-binfmt.service - Set Up Additional Binary Formats was skipped because of an unmet condition check (ConditionVirtualization=!wsl).
09:32:32 wsl-pro-service[173]: ERROR ... /mnt/c/WINDOWS/system32/cmd.exe: error: fork/exec /mnt/c/WINDOWS/system32/cmd.exe: exec format error.

09:32:02 首次启动时，wsl-pro-service 已经成功调用 cmd.exe 解析出了 Windows 侧的 $env:UserProfile 路径（/mnt/c/Users/<user>）；而在 09:32:19 实例经历一次关机与重启后，09:32:32 同一个服务再次调用 cmd.exe 就变成了 exec format error。

根因分析：为什么重启发行版会丢掉 WSLInterop

把 WSL 2 架构、systemd 关机源码和 Ubuntu 发行版补丁放在一起看，故障由两个环节共同触发：

1. systemd 关机流程清空了共享内核中的 binfmt_misc

WSL 2 的所有 Linux 发行版共享同一个轻量级工具虚拟机（Utility VM）内核，初始命名空间下的 /proc/sys/fs/binfmt_misc 注册表在虚拟机生命周期内是全局共享的。WSL 虚拟机冷启动时，根 init 进程会挂载 binfmt_misc 并写入 WSLInterop 规则，所以首次启动时即使不运行 systemd-binfmt.service，.exe 也能正常执行。

当启用了 systemd=true 的发行版实例单独终止或重启（底层 WSL 2 虚拟机并未随同冷重启）时，systemd 最后阶段会切换到 systemd-shutdown 进程。查看 systemd v255 源码 src/shutdown/shutdown.c 与 src/shared/binfmt-util.c：

int disable_binfmt(void) {
        int r;
        /* Flush out all rules. This is important during shutdown to cover for rules using "F", since those
         * might pin a file and thus block us from unmounting stuff cleanly. */
        r = binfmt_mounted();
        if (r <= 0)
                return r < 0 ? log_warning_errno(r, "Failed to determine whether binfmt_misc is mounted: %m") : 0;

        r = write_string_file("/proc/sys/fs/binfmt_misc/status", "-1", WRITE_STRING_FILE_DISABLE_BUFFER);
        if (r < 0)
                return log_warning_errno(r, "Failed to unregister binfmt_misc entries: %m");

        return 0;
}src/shared/binfmt-util.c

为了防止带 F（fix binary）标志的解释器句柄占用文件系统阻碍卸载，disable_binfmt() 会直接向 /proc/sys/fs/binfmt_misc/status 写入 -1，把内核里包括 WSLInterop 在内的全部注册项一次性清空。

2. wsl-setup 的旧版条件配置阻断了 WSL 的重注册钩子

WSL 针对 systemd 覆盖 binfmt_misc 的问题设计了 boot.protectBinfmt 机制（默认开启，见 src/linux/init/init.cpp），在每次启动发行版时动态生成 /run/systemd/generator/systemd-binfmt.service.d/override.conf：

  1. 用 ExecStop= 清空原本的 --unregister 停止命令；
  2. 追加命令重新向 /proc/sys/fs/binfmt_misc/register 写入 :WSLInterop:M::MZ::/init:P。

然而 Ubuntu 24.04 预装的 wsl-setup（0.5.4~24.04）包内置了 /lib/systemd/system/systemd-binfmt.service.d/wsl.conf（合并 /usr 后位于 /usr/lib/...），写有 ConditionVirtualization=!wsl。这是早期 WSL 尚未提供 generator 保护时留下的规避补丁，初衷是不让 systemd-binfmt 启动时改写 binfmt_misc。

在 systemd 的 drop-in 合并规则中，不同目录下的同名单元片段按文件名字母序依次加载：override.conf 先加载，wsl.conf 后加载，且 override.conf 只修改了 [Service] 段，没有重置 [Unit] 段的 ConditionVirtualization。最终 systemd-binfmt.service 在启动阶段因为 ConditionVirtualization=!wsl 不满足而直接跳过，WSL 准备好的重注册命令从未运行。

上游新版本的改进

在更新版本的 WSL 源码（如 3.0 系列，见 src/linux/init/init.cpp 的 ProtectBinfmtStatus()）中，WSL 进一步将普通文件 /run/wsl/binfmt-status-lock 以 MS_BIND 方式挂载覆盖到 /proc/sys/fs/binfmt_misc/status 上，使 systemd-shutdown 的 disable_binfmt() 只写到影子文件，不再清空虚拟机全局的 WSLInterop 注册表。在尚未包含该补丁的 WSL 2.7.3.0 上，仍需通过本地配置或升级 WSL 解决。

解决方案对比与实施

针对不同场景，可以选择以下三种处理方式：

方案持久性是否中断当前会话适用场景
/etc 覆盖 systemd-binfmt 配置永久生效，不受 apt upgrade 影响否保持当前 WSL 版本长期稳定使用
手动写入 /proc/sys/fs/binfmt_misc/register仅当前实例生命周期有效否临时应急恢复 .exe 调用
Windows 侧执行 wsl --shutdown 或 wsl --update重启仅单次恢复；升级到含 ProtectBinfmtStatus 的版本可根治是（会关闭所有 WSL 实例）允许中断工作流并更新 WSL 组件

推荐方案：通过 /etc 配置永久修复

不直接修改 /usr/lib/systemd/system/systemd-binfmt.service.d/wsl.conf（包管理器升级 wsl-setup 时会还原该文件），而是在 /etc 下做两处配置：

  1. 在 /etc/binfmt.d/WSLInterop.conf 写入 WSLInterop 规则，既保证 ConditionDirectoryNotEmpty=|/etc/binfmt.d 恒成立，又附加 F 标志使容器命名空间内也能复用解释器句柄；
  2. 创建 /etc/systemd/system/systemd-binfmt.service.d/zz-wsl-interop.conf，文件名以 zz- 开头确保按字典序排在 wsl.conf 之后（注意 - 的 ASCII 码 45 小于 . 的 46，若命名为 wsl-override.conf 会排在 wsl.conf 之前），用空值 ConditionVirtualization= 清空前置限制。

在 WSL 终端执行以下命令即可立即生效：

sudo mkdir -p /etc/binfmt.d /etc/systemd/system/systemd-binfmt.service.d && \
echo ':WSLInterop:M::MZ::/init:PF' | sudo tee /etc/binfmt.d/WSLInterop.conf >/dev/null && \
printf '[Unit]\nConditionVirtualization=\n' | sudo tee /etc/systemd/system/systemd-binfmt.service.d/zz-wsl-interop.conf >/dev/null && \
sudo systemctl daemon-reload && \
sudo systemctl restart systemd-binfmt.service
临时单次恢复命令

如果暂时不想改动 systemd 配置，也可以直接向内核注册接口写入规则，立即恢复当前会话的宿主机程序调用： echo ':WSLInterop:M::MZ::/init:PF' | sudo tee /proc/sys/fs/binfmt_misc/register

验证清单与边界说明

本次排查在非交互式会话中完成只读取证，修复命令需具备交互式 sudo 权限后执行：

  • 核实 /proc/sys/fs/binfmt_misc/ 仅剩 register 与 status（enabled），确认 WSLInterop 条目缺失。
  • 核实 /run/WSL/*_interop Socket 与 $WSL_INTEROP 环境变量存在，排除跨系统通信通道本身的异常。
  • 核实 systemctl cat systemd-binfmt.service 与 journalctl 启动日志，确认 09:32:19 关机重启后 ConditionVirtualization=!wsl 跳过了 systemd-binfmt.service。
  • 在交互终端执行 sudo 修复命令后，检查 /proc/sys/fs/binfmt_misc/WSLInterop 内容并运行 cmd.exe /c echo OK 与 code --version 验证调用恢复。
  • 执行 wsl --terminate Ubuntu 重新进入实例，确认单独重启发行版后 WSLInterop 仍会自动重建。

执行完修复命令后，可通过以下命令核验最终状态：

cat /proc/sys/fs/binfmt_misc/WSLInterop
cmd.exe /c echo OK
code --version

预期 /proc/sys/fs/binfmt_misc/WSLInterop 输出包含 enabled、interpreter /init 及 magic 4d5a，且 cmd.exe 与 code 正常返回结果。
